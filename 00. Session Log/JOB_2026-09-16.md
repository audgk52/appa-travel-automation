## 3. 오늘 내가 실제로 내린 결정 1–2개

### 결정 1 — Record identity와 logical stay grouping을 분리한다

`[AI→ME][DOMAIN]`

실제 Rooming List의 row 위치는 자주 바뀌기 때문에 physical row를 identity로 사용할 수 없다. 이에 따라:

- **`rooming_record_id`** = 하나의 operational Rooming List record를 추적하는 immutable technical identity
- **`stay_id`** = 같은 logical / continuous hotel stay에 속한 여러 `rooming_record_id`를 묶는 grouping identity

로 역할을 분리했다.

`stay_id`는 자동으로 확정하지 않는다. Agent가 traveler/date/contiguous boundary 등의 evidence로 grouping 후보를 제안할 수 있지만 **최초 grouping은 내가 확인하고, 확인된 membership만 persist**한다.

또한 `stay_id`는 자동 propagation authority가 아니다. 관련 record가 발견되면 **Detect → Suggest → Human confirms** 순서로 처리한다.

### 결정 2 — Yellow는 실시간 Agent marker가 아니라 on-demand accumulated change view다

`[ME][DOMAIN][AI→ME]`

Yellow의 의미를 다음처럼 정리했다.

**평소 manual / Agent changes 누적**  
→ 내가 `yellow 갱신해줘`라고 명시적으로 요청  
→ current Sheet와 active baseline 비교  
→ 누적 변경사항을 yellow로 표시  
→ 지배인님에게 변경사항 전달 / 확인  
→ 내가 `yellow reset해줘`라고 명시적으로 요청  
→ current state를 새 baseline으로 확정

Polling / on-edit auto refresh / automatic EOD reset은 넣지 않는다.

Yellow 비교에는 visible operational changes, `Total # of Nights`, `NTF Request History`를 포함하고 `rooming_record_id`, `stay_id`, `Row Number` 등 system/physical-location metadata는 제외하기로 했다.

## 4. 오늘 새로 이해한 것

`[AI→ME]` `rooming_record_id`만으로는 여러 row가 **같은 logical stay인지** 알 수 없다는 점을 이해했다. `rooming_record_id`는 “이 operational record가 이전에 보던 그 record인가?”를 해결하고, `stay_id`는 “이 여러 records가 하나의 stay 관계를 이루는가?”를 표현한다.

`[AI→ME]` `stay_id`의 목적은 dependent change를 자동으로 적용하는 것이 아니라, **관련 record를 발견하고 그 영향 가능성을 사람에게 보여주는 context**라는 점을 이해했다.

`[AI→ME]` optimistic concurrency에서는 revalidation과 post-write verification만으로 “사람의 최신 edit을 절대 덮어쓰지 않는다”는 보장을 할 수 없다. 시스템이 **관측한 newer state는 보호**할 수 있지만 final revalidation 이후 write 직전의 edit까지 막으려면 더 강한 locking/transaction mechanism이 필요하다. PG v1에서는 scope를 확장하지 않고 이 residual race를 명시적으로 수용했다.

`[AI→ME]` Yellow reset도 단순히 snapshot을 저장하고 색을 지우는 문제가 아니었다. 새 baseline이 **언제 authoritative해지는지**, render가 **어느 comparison snapshot 기준으로 정확한지**, reset 실패 시 **old/new baseline 중 무엇이 source of truth인지**까지 정해야 testable한 architecture가 된다는 점을 이해했다.

`[AI→ME]` Architecture Checkpoint의 목적은 edge case를 많이 나열하는 것이 아니라, **implementer가 expected behavior를 스스로 invent해야 하는 지점을 구현 전에 제거하는 것**이라는 점을 이번 반복 review를 통해 더 명확히 이해했다.

## 6. 예상과 달랐던 점 / 문제

`[AI→ME][DOMAIN]` 처음에는 persistent `stay_id`를 PG v1에서 defer할 수 있다고 생각했지만, 실제 업무에서 row restructuring이 자주 발생하고 같은 logical stay가 여러 coverage row로 나뉠 수 있다는 use case를 구체화하면서 **`rooming_record_id`와 `stay_id`가 서로 다른 문제를 해결한다는 구조**로 바뀌었다.

`[AI→ME]` 처음에는 “pre-write revalidation을 하면 newer human edit을 overwrite하지 않는다”고 강하게 표현할 수 있을 것처럼 보였지만, final revalidation과 실제 write 사이의 race window가 남는다는 점이 Formal Checkpoint에서 드러났다. 이에 따라 보장을 **never knowingly overwrite observed newer state**로 낮추고 residual race를 명시적으로 받아들였다.

`[AI→ME]` Yellow reset도 처음에는 `baseline 저장 → yellow clear` 정도로 생각했지만, reset 도중 failure나 concurrent edit이 발생할 때 어떤 baseline이 authoritative한지 애매해질 수 있다는 문제가 발견됐다. 최종적으로 baseline activation과 rendering cutoff를 분리한 snapshot semantics로 정리했다.

`[ME]` PRD가 v2 → v3 → v3.1 → v3.2까지 반복됐지만, 새로운 기능을 계속 추가한 것이 아니라 **Claude가 제품 행동을 추측해야 하는 부분을 하나씩 제거하는 과정**으로 받아들였다.
