## 4. Core Product Boundary — Human Judgment vs Automation

### Decision
**[DOMAIN][ME]** Hotel Ops should not try to automate hotel judgment. Its primary value is to compress the repetitive work that follows one human operational decision.

Target pattern:

`one human operational decision`  
→ Rooming List edit  
→ nights recalculation  
→ NTF Request History append  
→ yellow highlighting  
→ hotel-facing Kakao / email draft

### Why
Real hotel operations require judgment that depends on hotel availability, direct communication with the manager/reservations team, production coverage, payer responsibility, traveler preference, and production approval. Fully automatic hotel decisions would therefore increase correctness and authorization risk while solving the wrong problem.

The automation target is **human effort**, not human authority.

## 5. PG v1 Has Two Legitimate Entry Paths

### A. Itinerary-driven reconciliation
**[DOMAIN][ME]** When an original/revised itinerary arrives, PG should compare itinerary facts with the current Rooming List, derive deterministic changes, recalculate nights, surface policy implications, and ask only for decisions that require judgment.

### B. Quick Ops Change
**[DOMAIN][ME]** Many real changes do not originate from a new itinerary. During production, Myungha often decided small changes directly with the hotel through KakaoTalk/email and then manually repeated the same updates in the Rooming List.

Examples include:
- check-in / check-out changes;
- late checkout requests;
- room changes;
- extra-bed setup;
- payment changes;
- extensions / shortenings;
- other room-specific operational instructions.

Therefore Quick Ops is **not scope creep**. It is a second input path into the same business operation.

Both paths must converge on one structured `RoomingChange` proposal so the Sheet update, nights, history, highlighting, Kakao draft, and email draft cannot drift apart.

## 6. Early Check-in Policy and Decision Boundary

**[DOMAIN] Hotel policy supplied by Myungha:**

- Before 09:00 → previous-night guarantee; 100% nightly charge.
- 09:00–12:00 → previous-night booking/check-in date; 50% nightly charge.
- After 12:00 → no early-check-in charge; subject to room availability.

**[DOMAIN][ME] Decision boundary:** the policy result is a **possible / recommended rooming implication**, not an automatic booking commitment.

Final action may depend on:
- whether the period is production-covered or personal-pay;
- production approval when production pays;
- traveler preference when self-paid;
- hotel availability.

PG should make the implication visible and ask for explicit confirmation/override before write.

Open domain checks to close in the PRD:
- exact 09:00 / 12:00 boundary semantics;
- whether expected hotel-arrival time is explicitly entered or inferred and confirmed;
- how `Total # of Nights` is defined when a previous-night booking has a 50% charge;
- exact destination/semantics of late-checkout status;
- exact yellow-highlight lifecycle.

## 7. TBD / Speculative Room Holds

### Decision
**[ME]** Speculative/TBD room-capacity planning remains manual in PG v1.

### Rationale
Room holds are created before flight booking based on expected stays, hotel inventory, budget, and production judgment. This is a planning / negotiation task, not merely a deterministic follow-up update.

To protect the A→Z skeleton strategy, PG v1 will not automate:
- creation of TBD holds;
- TBD assignment / reassignment / release;
- stay creation / splitting / merging;
- row restructuring.

These may be revisited after the shared canonical identity/data layer is built.

## 8. Identity Decision — Bounded v1, Durable Identity Later

### Astra architecture review result
A focused Astra Medium review conditionally approved the minimal PG v1 boundary.

**[AI]** `StaySegment` is a useful internal domain concept now, but persistent `stay_id` can be deferred as long as PG remains a bounded workflow operating on an explicitly identified existing stay.

For PG v1:
- mutable sheet fields are locator evidence, not durable identity;
- a traveler-level match is insufficient;
- zero or multiple plausible rows must stop automatic targeting;
- ambiguous cases require explicit user selection;
- the selected row plus its observed current values must be retained with the proposal.

Persistent `stay_id` should be revisited when the shared canonical layer needs continuity across renamed travelers, reconstructed rows, reassigned TBD inventory, split/merged stays, or cross-system operations.

**Important:** durable identity would not replace stale-state validation. Identity answers “which entity”; state validation answers “is the approved proposal still current?”

## 9. New Correctness Guardrail: Proposal Binding + Pre-write Revalidation

**[AI] pending implementation / UAT validation.**

PG interaction may be:

`read current row → generate proposal → user reviews → user approves → write`

A human may modify the sheet between proposal generation and commit. Therefore PG v1 should:

1. bind confirmation to the exact target and exact proposed values shown;
2. retain relevant observed current values with the proposal;
3. re-read the target immediately before commit;
4. if relevant state has changed, stop and regenerate rather than silently overwrite.

This is intentionally a lightweight stale-write safeguard, not a generalized transaction framework.

Additional v1 guardrails from the architecture review:
- repeat/retry safety so history is not duplicated or a change applied twice;
- explicit complete / incomplete / uncertain execution outcomes;
- truthful message drafts — a hotel request must not be represented as hotel confirmation;
- preserve existing history, formulas, and unrelated formatting.
